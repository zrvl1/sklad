# Склад для SalesDrive

Веб-додаток поруч із SalesDrive: додавання товарів, прихід товару, комірки, друк цінників і етикеток, журнал і звіти.
Стек: Next.js 15 (App Router) + React 19 + Prisma + PostgreSQL (Neon), хостинг Vercel.

## Як це пов'язано з SalesDrive

| Що | Як |
|---|---|
| Читання товарів і залишків | YML-посилання SalesDrive → кнопка «Завантажити товари» в Налаштуваннях |
| Створення / зміна товару | API `product-handler` — товар одразу з'являється в CRM |
| Прихід | Документ зберігається в нашій базі. Після «Провести» в CRM оновлюються **залишок, собівартість і (за бажанням) ціна** |
| Комірки, журнал приходів, журнал дій, звіти | Лише в нашій базі |

Чому прихід не створюється як документ «Надходження» в самій CRM: публічне API SalesDrive дозволяє такі документи
лише **читати** (список), а створювати — ні. Якщо SalesDrive додасть метод створення, його легко дописати
у `src/app/(app)/receipts/actions.ts` → `postReceipt`.

## Як влаштовано на сервері

```
Співробітники (ПК, телефон) ──HTTPS──> Vercel (сайт, регіон Франкфурт)
                                          ├── Neon PostgreSQL (база, Франкфурт, резервні копії)
                                          └── SalesDrive API + YML (кожні 30 хв автосинхронізація)
```

Захист:
- лише HTTPS, cookie сесії `httpOnly` + `secure`, сесія живе 14 днів;
- паролі зберігаються як хеш scrypt, мінімум 10 символів;
- блокування після 5 невдалих спроб входу на логін або 20 з однієї IP за 15 хв, журнал спроб у Налаштуваннях;
- зміна пароля чи блокування користувача завершує всі його сесії;
- заголовки безпеки (CSP, HSTS, X-Frame-Options), сайт закритий від пошукових систем;
- кожна дія перевіряє вхід користувача, журнал дій фіксує хто і що робив;
- секрети (ключ SalesDrive, YML, паролі бази) лише в змінних середовища Vercel, не в коді;
- ключ SalesDrive з мінімальними правами: товари й категорії без видалення, без доступу до заявок, чеків, Checkbox.

## Розгортання (один раз)

1. **Neon** (neon.com): New project → регіон **AWS Europe Central 1 (Frankfurt)** → Connect: скопіюйте рядок
   з `-pooler` (DATABASE_URL) і без нього (DIRECT_URL, перемикач «Connection pooling» вимкнути).
2. **Код на GitHub** у **приватному** репозиторії.
3. **Vercel** (vercel.com, вхід через GitHub): Add New → Project → імпорт репозиторію → Environment Variables:
   усі змінні з `.env.example` (`COOKIE_SECURE` не потрібна) → Deploy.
4. Під час кожної публікації сервер сам оновлює структуру бази (`prisma db push`; зміни з втратою даних не застосовуються —
   публікація тоді зупиниться з помилкою) і створює адміністратора з `ADMIN_LOGIN`/`ADMIN_PASSWORD`, якщо його ще немає.
5. Відкрийте адресу сайту, увійдіть, Налаштування → завантажити товари, створити комірки й постачальників.

Після цього кожна зміна коду в GitHub автоматично публікується на сайті за 1–2 хвилини. У Vercel → Deployments
будь-яку попередню версію можна повернути кнопкою «Promote to Production».

## Локальна робота (для перевірки змін)

`.env` на ПК вказує на гілку **dev** у Neon, тож експерименти не чіпають робочі дані.
```
npm install
npm run db:push
npm run db:seed
npm run dev
```

## Перший запуск — порядок дій

1. **Налаштування → Завантажити товари з SalesDrive.**
2. Перевірте кілька товарів: чи підтягнулися штрихкод, SKU, ціна, залишок. Якщо щось порожнє — запустіть
   `npm run yml:inspect`, подивіться назву тегу і допишіть її в `parseYml` (`src/lib/salesdrive.ts`).
3. **Налаштування → Склади:** склад «Основний» позначено як «за замовчуванням». Якщо у SalesDrive кілька складів —
   вкажіть «ID у SalesDrive» (там же, де ключ API).
4. **Комірки:** створіть сіткою (A-01-1 … A-05-4) і роздрукуйте етикетки на полиці.
5. **Тест на одному товарі:** змініть ціну тестового товару в нашому додатку і перевірте в SalesDrive, що зміна дійшла
   і нічого зайвого не затерлося. Лише після цього проводьте реальні приходи.

## Склад і комірки

- **Склад і комірки** (меню): пошук «де лежить» (скан або назва), карта комірок по зонах, список «не розкладено».
- Комірка: скануйте товар — він додається в комірку; переміщення в іншу комірку, коригування кількості, історія операцій.
- Відскануйте етикетку комірки на сторінці складу — комірка відкриється одразу.
- Після продажу в CRM залишок у SalesDrive зменшується; під час синхронізації додаток так само зменшує кількість у комірках
  (спершу там, де лежить найменше) і пише це в журнал. Прив'язка товару до комірки (місце) зберігається.

## Коди товару

- Штрихкод і артикул (SKU) — основні, ідуть у SalesDrive. ID — поле «ID» SalesDrive (для нових товарів `W000123`).
- **Артикули постачальників і додаткові штрихкоди** — скільки завгодно на товар, пошук працює за всіма.
- Невідомий код у приході/інвентаризації → «Прив'язати до наявного товару» або «Створити новий».
- **Штрихкоди й артикули** (меню): шаблон артикула (префікс + номер), масова генерація штрихкодів EAN-13 (префікс 200)
  і артикулів для товарів без них, пошук дублікатів.

## Валюти (вимкнено)

Код для закупівлі у валюті є, але прихований. Увімкнути: `ENABLE_CURRENCY="true"` і право ключа «Курси валют: читання».

## Постійний обмін із SalesDrive

- Під час роботи з додатком дані оновлюються автоматично кожні 15 хвилин (у фоні), на сервері — ще й за розкладом.
- Оновлюються назви, ціни, коди, категорії, залишки, опис і характеристики (якщо в YML увімкнено «опис, фото та характеристики»).
- Зміни з додатку (створення, редагування, прихід, списання, інвентаризація, видалення) одразу йдуть у SalesDrive.
  Назва, ціна, собівартість, опис і характеристики відправляються лише коли змінені.

## Видалення товарів

- Видалити можна на картці товару або кілька зі списку (менеджер/адмін). Товар видаляється в SalesDrive
  (ключу потрібне право «Товари: видалення»), а в додатку ховається — історія приходів і продажів зберігається.
- Якщо товар видалили прямо в SalesDrive, синхронізація це помітить сама. Захист: якщо YML раптом прийшов без >20% товарів,
  нічого не позначається (схоже на збій).
- **Видалені товари** (меню): журнал з усіма даними (ID, артикул, штрихкод, назва, ціна, категорія) і статусом для кожного сайту
  (Prom, Horoshop — список сайтів налаштовується): «треба видалити» → «видалено» / «не було». CSV для кожного сайту,
  лічильник у меню й на головній, щоб не забути. Помилково видалений товар можна відновити.

## Шаблони опису й характеристик

- **Шаблони опису** (меню): для категорії або загальний — опис з підстановками `{name} {sku} {manufacturer} {category} {supplier} {barcode}`,
  характеристики (назва, тип, значення), виробник і постачальник за замовчуванням.
- Новий товар (у формі, у приході, в інвентаризації): обрали категорію — поля підставляються. Введене вручну не замінюється.
- «Застосувати до наявних товарів» заповнює товари категорії з порожнім описом/характеристиками і відправляє в SalesDrive
  (лише коли YML віддає опис і характеристики).
- Характеристики відправляються в режимі заміни, якщо ми знаємо всі характеристики товару з YML, інакше — в режимі додавання.
  Порожній список ніколи не відправляється.

## Списання

Причина (брак, втрата, пересорт, власні потреби, повернення постачальнику…), сканування товарів, комірка (або автоматично
звідки лежить). Не дає списати більше, ніж є. Проведення зменшує залишок у SalesDrive і в комірках, пише рух товару.
Список списань із сумами за причинами.

## Інвентаризація

Скануйте комірку, потім товари (кожен скан = +1). Видно розбіжності «облік / факт». Проведення встановлює в SalesDrive
залишок = пораховано лише для порахованих товарів; можна проводити частинами. Опція «комірки перераховано повністю»
прибирає з комірок те, чого не відскановано.

## Звіт по продажах

Окремий ключ SalesDrive лише на читання заявок і статусів (`SALESDRIVE_ORDERS_KEY`). Зберігаються лише товари, суми, статуси —
без даних клієнтів. Звіт: виручка, собівартість, прибуток, топ товарів і категорій, «що закупити», неліквід.
Обробка заявок, ТТН і SMS залишаються в SalesDrive.

## Перевірки (щоб нічого не зламати)

- Штрихкод і артикул перевіряються ще під час введення: зайнятий іншим товаром — форма не збережеться (з посиланням на той товар);
  неправильна контрольна цифра EAN-13 — теж блокує. На сервері те саме перевіряється вдруге.
- Ціна/собівартість — лише додатні числа, знижка 0–99%, дати знижки в правильному порядку.
- Прихід: попередження про нульову закупівлю, закупівлю вищу за ціну продажу, різницю з попередньою закупівлею >50%,
  дробову чи дуже велику кількість — список показується перед проведенням.
- Інвентаризація: великі розбіжності показуються окремо перед проведенням.
- Списання: не дає списати більше, ніж є.
- Видалення: товар із залишком видаляється лише після окремого підтвердження; видалені товари не можна провести в документах.
- Подвійне натискання «Провести» не проводить документ двічі; якщо SalesDrive не прийняв дані — документ лишається чернеткою.

## Друк наліпок 40×25

Шаблон за замовчуванням — 40×25: назва (2 рядки), штрихкод, артикул, ціна (зі старою закресленою, якщо знижка).
Комірка — опційно (галочка «комірка на наліпці»): для цінника на товарі її краще не друкувати, бо товар переміщують;
для наліпок на коробки/полиці складу — можна.

Налаштування принтера (Xprinter / TSC / Zebra тощо):
1. Встановіть драйвер принтера, у властивостях драйвера створіть розмір паперу 40×25 мм, тип — етикетки з проміжком (gap).
2. Відкалібруйте датчик проміжку (зазвичай кнопкою FEED на увімкненому принтері або з утиліти драйвера).
3. У додатку відкрийте «Тестова наліпка» → Друкувати. У вікні друку Chrome: принтер етикеток, «Більше налаштувань» →
   розмір паперу 40×25, поля «Немає», масштаб 100%, без колонтитулів.
4. Якщо друк зміщений — виставте зсув X/Y у панелі друку (запам'ятовується для цього шаблону). Галочка «друкувати рамку» допомагає побачити межі.
5. Без діалогу друку: ярлик Chrome з ключем `--kiosk-printing` і принтер етикеток за замовчуванням у Windows.

## Комірки в різних процесах

| Процес | Чи потрібні комірки | Як працює |
|---|---|---|
| Прихід | Бажано | Відскануйте етикетку комірки — наступні товари падають у неї. Можна не вказувати й розкласти пізніше зі списку «Не розкладено». |
| Продаж (заявки в SalesDrive) | Для збирання — так | Див. «Збирання і пакування» нижче. Після відвантаження залишок у CRM зменшується, і додаток сам зменшує кількість у комірках. |
| Інвентаризація | Рекомендовано | Рахуйте комірку за коміркою: так видно не лише нестачу, а й де саме лежить товар. |
| Списання | Не обов'язково | Можна вказати комірку, інакше списується автоматично з тієї, де лежить. |
| Переміщення | Так | Сторінка комірки → «Перемістити». |
| Цінники, ціни, опис, видалення | Ні | Комірки на це не впливають. |

## Ролі

| Роль | Що може |
|---|---|
| Адміністратор | Усе: товари, комплекти, прихід, комірки, наліпки, звіти, налаштування, користувачі |
| Комірник (склад) | Прихід, інвентаризація, списання, комірки, наліпки, збирання й пакування; прив'язує коди постачальників до наявних товарів. Не створює й не видаляє товари, не бачить звітів і налаштувань |
| Менеджер (заявки й пакування) | Збирання й пакування, пошук товару, комірка, опис і характеристики (для дзвінків), друк наліпок. Не бачить закупівель, собівартості, звітів; не змінює товари |

Обмеження перевіряються на сервері (не лише сховані кнопки). Нові товари створює лише адміністратор: у приході
невідомий код інші ролі можуть тільки прив'язати до наявного товару.

## Основний товар і картки-комплекти

Один фізичний товар у SalesDrive зібраний у кілька карток (різні назви/описи під моделі для SEO), кожна зі своїм ID,
штрихкодом і артикулом. У додатку картка прив'язується до основного товару («Комплекти (картки)»: автопошук за артикулом
`CM0361-2` → `CM0361`, або вручну в картці товару).

- Прихід, інвентаризація, списання, комірки: скан коду будь-якої картки підставляє основний товар; залишок пишеться лише основному.
- Наліпки: друкується наліпка основного товару; під час пакування вона підходить до замовлення на будь-яку його картку.
- Збирання: картки збираються з комірок основного товару.
- Ціна: нова ціна основного товару (у картці чи в приході) переноситься на всі його картки.
- Список товарів без пошуку показує лише основні товари з позначкою «+N карток».
- Звіт: продажі карток зараховуються основному в «Що закупити» і «Неліквід».
- Нові картки-комплекти створюються в SalesDrive (галочка «Комплект»): API SalesDrive не має поля складу комплекту.
  Якщо артикул картки `ОСНОВНИЙ-N`, після синхронізації вона з'явиться в «Комплекти (картки)» для прив'язки одним кліком.
- Пакування: для картки-комплекту видно «Фізично: <основний товар>» і після скану — «✓ Правильний товар».

## Збирання і пакування (заявки лишаються в SalesDrive)

1. У SalesDrive: опрацювали заявку, створили ТТН, статус «На відправку», масово надрукували ТТН — як і раніше.
2. **Збирання замовлень**: «Оновити з SalesDrive» → усі заявки «На відправку», ще не запаковані. Друкуєте спільний список,
   відсортований за комірками, і збираєте все за один прохід.
3. **Пакування**: скан штрихкоду ТТН → відкривається замовлення → скан кожного товару в пакунок (чужий/зайвий — червоним зі звуком)
   → коли все сходиться, замовлення позначається «запаковано» → клеїте ТТН, наступна.
4. Далі статуси оновлює пошта; заявка йде зі списку. «Продано» рахується продажем у звіті, «Відмова» — товар повертається:
   залишок у SalesDrive зросте, і товар з'явиться в «Не розкладено», щоб покласти його назад у комірку.

Нова пошта: штрихкод на ТТН — це номер ТТН (14 цифр). Укрпошта: номер зберігається як є (цифри або RR…UA), тож після
підключення інтеграції в SalesDrive запрацює без змін. Якщо ТТН ще не підтягнулась, пакування саме оновить заявки з SalesDrive.

## Як працює прихід

1. «Новий прихід» → обрати склад, постачальника, № накладної.
2. Скануйте штрихкоди (USB-сканер працює як клавіатура). Повторне сканування збільшує кількість.
   Нового товару немає — «Новий товар» прямо в документі (штрихкод згенерується автоматично).
3. Вкажіть закупівельну ціну, за потреби нову ціну продажу і комірку.
   Відскануйте етикетку комірки — наступні товари автоматично розкладуться в неї.
4. «Провести»: додаток оновлює залишки з SalesDrive, додає прихід, відправляє в CRM залишок, собівартість і ціну,
   записує товар у комірки. Якщо CRM не прийняла дані — документ лишається чернеткою, нічого не змінюється.
5. Після проведення — кнопка «Цінники на прихід» (кількість цінників = кількості товару).

## Друк цінників

- **Товари → позначити → «Друкувати цінники»** або кнопка на картці товару / в проведеному приході.
- Шаблони: 58×40, 58×30, 40×30, 30×20 (термопринтер) і A4 3×8. Свій розмір — додайте в `src/lib/labels.ts`.
- Діє знижка — на цінник виводиться стара ціна закресленою і нова.
- У вікні друку: принтер етикеток, масштаб 100 %, поля «Немає».
- Друк без діалогу: створіть ярлик Chrome з ключем `--kiosk-printing` (друкує на принтер за замовчуванням).

## Обмеження цієї версії (і що робити далі)

- **Кілька складів.** YML віддає загальний залишок, тому проводити прихід поки можна лише на склад за замовчуванням
  (інакше можна затерти чужий залишок). Наступний крок — читати залишки по складах.
- **Залишок записується абсолютним числом.** Перед проведенням ми оновлюємо залишки з YML, але якщо продаж
  відбувся саме в ці секунди і YML ще не оновився, можлива невелика розбіжність. Для спокійного складу це рідкість.
- **ID нових товарів** генерується як `W000123`. Якщо у вас є своя схема ID — змініть у `finalizeNewProduct`.
- **Знижка** надсилається як `10%` або сумою — перевірте на тестовому товарі, що SalesDrive розуміє формат.

## Структура

```
prisma/schema.prisma          — таблиці: товари, склади, комірки, приходи, витрати, журнал дій
src/lib/salesdrive.ts         — API SalesDrive і розбір YML
src/lib/sync.ts               — синхронізація товарів
src/app/(app)/products        — список, картка, створення товару
src/app/(app)/receipts        — журнал і документ приходу (actions.ts — логіка проведення)
src/app/(app)/reports         — звіт по приходах
src/app/(app)/settings        — склади, комірки, постачальники, користувачі, журнал дій
src/app/print/labels          — друк цінників
src/app/print/cells           — етикетки комірок
src/app/api/receipts/export   — експорт приходів у CSV (Excel)
```
